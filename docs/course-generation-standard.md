# 课程内容生成标准

本文件是后续所有课程内容生成任务的总规范。处理任何新课程前，内容生成模型必须先阅读本文件，再根据 `source-materials/{courseSlug}/` 生成 `data/generated/{courseSlug}/sample/` 或 `data/generated/{courseSlug}/full/`。如果用户没有特别说明，应优先遵守本文件。

本标准面向 `study-ai-mvp` 的离线课程内容生产流程。它不是验收清单，而是 Codex / GPT Pro 在处理新课程 PDF、PPT、Word 或其他课程资料时必须遵守的固定生成规范。

## 1. 总目标

课程内容生成的目标不是普通摘要，也不是把课件逐页转写成网页文本。目标是把原始课程资料整理成适合期末复习网站使用的结构化学习内容，让学生能够快速把握章节主线、理解关键机制、复习公式计算，并通过案例、例题和可视化内容建立可考试、可回忆、可应用的知识框架。

生成内容应尽量包含：

- 章节主线：本章讲什么、解决什么问题、在整门课中承担什么作用。
- 核心概念：重要术语、定义、概念边界、概念之间的关系。
- 公式与计算：公式本体、变量含义、适用条件、计算方向和易错点。
- 案例与例题：直接面向学生的案例材料和计算例题。
- 数据表：课程资料中的重要数据、现金流表、比较表、策略表。
- 流程图：交易机制、清算机制、套利过程、对冲过程、风控过程。
- 现金流图：互换、远期、货币交换、中央清算、风险转移。
- 收益图：期权头寸、期权策略、价差组合、保护性组合等。
- 判断路径：套利方向、对冲方向、期权执行、策略选择。
- 时间线：交易生命周期、合约到期过程、现金流支付周期。
- 复习路径：学生应该先理解什么、再掌握什么、最后用于什么。

任何内容都必须服务于复习。不要把页面写成资料解读报告，也不要把页面写成题库。

## 2. 内容生产流程

标准流程如下：

`source-materials/{courseSlug}/`
→ `data/generated/{courseSlug}/sample/`
→ `data/generated/{courseSlug}/full/`
→ schema 校验
→ `/admin/preview/generated` 预览
→ 人工审核
→ 导入数据库
→ `/framework` 学生端展示

`sample` 是单章样板。处理新课程时，应先选择一份最适合作为样板的章节资料，生成 `sample` 版本，用于验证章节结构、案例口吻、公式格式、visualBlocks 使用方式和页面展示效果。

`full` 是整门课程候选内容。只有在 sample 标准被确认后，才基于同一标准处理整门课程资料，生成 `full` 版本供预览和审核。

除非用户明确要求，生成阶段不得导入数据库，不得修改学生端页面，不得修改 Prisma schema，不得调用在线 AI API。

## 3. 输出文件规范

每个 `sample` 或 `full` 目录应尽量包含以下文件：

- `materials.json`：记录本轮处理的资料清单，包括资料名称、课程归属、文件路径、资料类型和处理状态。
- `chunks.json`：记录从资料中抽取和整理出的内容块。chunk 应保留内部溯源能力，但不要把来源信息写入学生可见的 framework 文本。
- `framework-concise.json`：考前快速复习版本，结构更短，保留主线、核心概念、关键机制、核心公式和最重要 visualBlocks。
- `framework-detailed.json`：系统学习版本，结构更完整，展开概念关系、机制流程、公式逻辑、案例、例题、图表和复习路径。
- `import-summary.md`：说明本轮生成内容的范围、章节、文件、导入前注意事项和预览方式。
- `quality-review.md`：记录内容质量、可视化重建情况、无法确认的资料、需要人工审核的问题和校验结果。
- `CHANGELOG.md`：可选。用于记录多轮人工反馈后的内容调整历史。

生成文件必须写入指定课程目录，例如 `data/generated/{courseSlug}/full/`。不要覆盖其他课程、旧路径或已确认的 sample 内容。

## 4. concise 和 detailed 区别

`framework-concise.json` 面向考前快速复习。它应当短、清晰、抓主线，帮助学生在有限时间内回忆本章考点。concise 应保留最关键的概念、机制、公式、易混点和少量高价值 visualBlocks，不要塞入所有案例和所有图表。

`framework-detailed.json` 面向系统学习。它应当更完整，但不能变成长文堆砌。detailed 应展开概念关系、机制流程、公式逻辑、案例材料、计算例题、数据表、现金流图、收益图和复习路径，让学生能够从头学懂一章。

concise 不能只是 detailed 的机械截断版。它需要重新组织为快速复习视角。

detailed 不能只是课件内容的长段落搬运。它需要结构化、层级化、可视化。

## 5. 每章标准结构

每章应尽量遵循以下结构，但可根据课程类型适度调整。

### 5.1 章节总览

说明本章一句话定位、本章在整门课中的作用、本章主线。章节定位不能和具体知识点并列堆放，应放在 summary 或总览节点中。

### 5.2 核心概念

列出本章必须掌握的术语、定义、边界和相互关系。并列概念优先用 `comparison_table`、`concept_map` 或 `data_table` 表达，不要误画成流程。

### 5.3 核心机制

说明本章最重要的运行机制、操作逻辑或制度安排。例如交易流程、清算流程、保证金机制、套利机制、风险转移机制等。机制流程优先使用 `process_flow`、`timeline` 或 `cashflow_diagram`。

### 5.4 公式与计算逻辑

整理公式、变量、适用场景、计算步骤和常见错误。重要公式必须使用 `formula_card`，并尽量配套 `example_box`。

### 5.5 案例与例题

将课程资料中的案例、课堂例子、市场事件、计算例题转成学生可直接阅读的 `case_card` 或 `example_box`。不要写成“资料说明了什么”的报告口吻。

### 5.6 图表化理解

对原资料中的表格、流程图、收益图、曲线图、现金流图、结构图进行最大程度重建。能用 visualBlocks 表达的，优先转成 visualBlocks。无法可靠重建的，写入 `quality-review.md`。

### 5.7 易混点

整理容易混淆的概念、公式、交易方向、收益方向和适用条件。例如远期与期货、初始保证金与维持保证金、平仓与交割、看涨与看跌、买方与卖方。

### 5.8 复习路径

给出学生复习本章的顺序。复习路径应是学习建议，不是题库，不要生成练习题。

## 6. 案例生成标准

`case_card` 应像案例材料，不像资料解读报告。它必须让学生直接读到“发生了什么、冲突在哪里、金融机制是什么、复习要抓什么”。

`case_card` 必须包含：

- `background`：案例背景。交代参与方、市场环境或基本事实。
- `scenario`：具体情境或冲突。说明风险、价格偏离、现金流冲突、违约、策略选择等问题如何出现。
- `analysis`：金融机制分析。必须解释这个案例如何体现课程概念，不能停留在泛泛背景。
- `lesson`：复习启示。指出学生应从案例中掌握的考试或理解重点。
- `relatedConcepts`：相关概念。列出与本案例直接相关的术语。

禁止使用以下报告口吻：

- 课件展示了……
- 资料中显示……
- 这个案例说明了……
- 用来说明……
- 需要强调……
- 该事件背景是……

错误示例：

```json
{
  "type": "case_card",
  "title": "雷曼兄弟案例",
  "background": "资料中展示了雷曼兄弟破产事件。",
  "scenario": "该事件背景是金融危机。",
  "analysis": "这个案例说明了衍生品风险很大。",
  "lesson": "需要强调风险管理。",
  "relatedConcepts": ["风险管理"]
}
```

正确示例：

```json
{
  "type": "case_card",
  "title": "案例 1：雷曼兄弟与场外衍生品风险",
  "background": "雷曼兄弟在场外衍生品市场中持有大量未到期交易合约，交易对手数量多，合约关系复杂。",
  "scenario": "当信用状况恶化并最终破产时，交易对手需要重新估值合约、终止或替代交易，并承担可能出现的违约损失。",
  "analysis": "场外衍生品缺少交易所集中清算时，交易双方直接承担对方违约风险。合约规模越大、交易对手越多，替代交易成本、信用暴露和风险传导越难管理。",
  "lesson": "复习本案例时，应抓住交易对手风险、信用风险暴露和中央清算机制之间的关系。",
  "relatedConcepts": ["场外衍生品", "交易对手风险", "信用风险", "中央清算"]
}
```

## 7. 例题生成标准

`example_box` 应像教材例题、课堂例题或考试材料题，而不是资料摘要。

`example_box` 应尽量包含：

- 已知条件
- 问题 / 判断任务
- 解法步骤
- 计算或判断
- 结论
- 复习启示

`example_box` 即使当前 schema 没有 question 字段，也必须显式写出问题 / 判断任务。可以写在 `scenario` 中，也可以作为 `steps` 的第一项。不能只给已知条件、计算步骤和结论。

错误示例：

```json
{
  "type": "example_box",
  "title": "黄金远期例子",
  "scenario": "已知黄金即期价格为 1,400 美元、1 年期无风险利率为 5% 的例子，用来判断远期价格是否存在套利机会。",
  "steps": ["代入公式计算。"],
  "result": "可以判断套利方向。",
  "takeaway": "这个例子用来说明无套利定价。"
}
```

正确示例：

```json
{
  "type": "example_box",
  "title": "例子 1：黄金远期套利判断",
  "scenario": "已知条件：黄金即期价格为 1,400 美元，1 年期无风险利率为 5%，市场存在一个 1 年期远期报价。问题：市场远期价格是否偏离理论价格？如果偏离，应如何构造套利？",
  "steps": [
    "使用无收益资产远期定价公式：\\(F_0 = S_0 e^{rT}\\)。",
    "代入参数：\\(S_0 = 1400\\)、\\(r = 5\\%\\)、\\(T = 1\\)。",
    "计算理论远期价格：\\(F_0 = 1400e^{0.05}\\)。",
    "将理论远期价格与市场远期报价比较。",
    "如果市场远期价格高于理论价格，考虑买入现货并卖出远期；如果市场远期价格低于理论价格，考虑反向套利。"
  ],
  "result": "套利方向取决于市场远期价格相对理论价格的偏离方向。",
  "takeaway": "远期定价题的核心是“理论价格—市场报价—套利方向”的判断链条。"
}
```

例题不得写成题库。可以有“问题 / 判断任务”，但不要生成选择题、判断题、简答题或练习题集合。

## 8. 公式生成标准

重要公式应使用 `formula_card`。`formula_card` 应尽量包含：

- `formula`：普通文本公式，作为 fallback。
- `formulaLatex`：KaTeX 可渲染的 LaTeX 公式本体，不要写 `$$...$$`，不要写 `\\[...\\]`。
- `variables`：变量含义，变量符号尽量使用规范数学写法。
- `usage`：适用场景。
- `pitfalls`：常见错误。

正文、表格和例题中的公式使用 inline LaTeX：`\\( ... \\)`。

禁止：

```text
F0 = S0 e^(rT)
max(ST-K,0)
N* = hA QA / QF
```

推荐：

```text
\\(F_0 = S_0 e^{rT}\\)
\\(\\max(S_T-K,0)\\)
\\(N^* = h_A Q_A / Q_F\\)
```

常见金融公式符号规范：

- 远期或期货价格：`\\(F_0\\)`
- 现货价格：`\\(S_0\\)`
- 到期标的价格：`\\(S_T\\)`
- 执行价格：`\\(K\\)`
- 无风险利率：`\\(r\\)`
- 期限：`\\(T\\)`
- 连续收益率或股息收益率：`\\(q\\)`
- 已知现金收益现值：`\\(I\\)`
- 看涨期权费：`\\(c\\)`
- 看跌期权费：`\\(p\\)`
- 波动率：`\\(\\sigma\\)`
- 最优套期保值比率：`\\(h^*\\)`
- 最优合约数量：`\\(N^*\\)`
- 合约规模：`\\(Q_F\\)`
- 被套期资产规模：`\\(Q_A\\)`

## 9. 最大程度可视化原则

禁止空引用，不等于禁止图表。

“不要空引用”的意思是：不要写“如图2.1所示”“见表2.1”“图中显示”“如下表”，但网页里没有对应图表或等效可视化。

正确做法是最大程度保留和重建原资料中的图、表、案例、数据、流程图、收益图、现金流图和结构图。

处理规则：

1. 原资料有图表，优先重建为 visualBlock。
2. 无法直接复现原图时，生成等效图表，保留其学习价值。
3. 无法确认具体数据时，不编造数字。
4. 无法可靠重建时，写入 `quality-review.md`，说明需要人工截图、人工补充或人工核对。
5. 不要因为避免空引用而删除图表承载的知识。
6. 只有确实存在可用图片文件路径时，才使用 `image` block；不要伪造图片路径。

常见处理方式：

- 原 PDF 有表格：能确认数据就用 `data_table` 重建；不能确认完整数据时，用 `comparison_table` 或文字化 `data_table` 表达结构关系，并标记待核对。
- 原 PDF 有流程图：理解机制后用 `process_flow` 或 `timeline` 重建。
- 原 PDF 有收益图：用 `payoff_chart` 重建收益形状，必要时使用标准化示意点，并明确不是市场真实数据。
- 原 PDF 有曲线图：用 `line_chart` 或 `curve_chart` 表达趋势、曲线方向和关键关系。
- 原 PDF 有现金流结构图：用 `cashflow_diagram` 表达节点、支付方向、现金流类型和复习结论。
- 原 PDF 有长文本案例：用 `case_card` 重写为背景、情境、分析和复习启示。
- 原 PDF 有数值计算：用 `example_box` 重写为条件、问题、步骤、结果和启示。
- 原 PDF 有公式推导：用 `formula_card` 加结构化说明，必要时配合 `process_flow` 表达推导逻辑。

## 10. visualBlock 选择规则

生成 visualBlocks 前，必须先判断内容关系类型，再选择 block。不要为了“有图”而误用箭头、流程或判断树。

### 10.1 并列分类 / 对比关系

适用内容：

- 看涨 vs 看跌
- 买方 vs 卖方
- 远期 / 期货 / 期权 / 互换
- 买入看涨 / 卖出看涨 / 买入看跌 / 卖出看跌
- 牛市价差 / 熊市价差 / 跨式 / 宽跨式 / 蝶式
- 不同风险类型
- 不同合约类型

应使用：

- `comparison_table`
- `concept_map`
- `data_table`

不要使用：

- `process_flow`
- `timeline`
- `decision_tree`
- `cashflow_diagram`

并列概念不能用箭头流程展示。

### 10.2 时间顺序

适用内容：

- 期货建仓 → 每日盯市 → 追加保证金 → 平仓 / 交割
- 远期签约 → 持有 → 到期交割
- 货币互换期初本金交换 → 存续期利息交换 → 到期本金返还
- 期权建仓 → 持有 → 到期行权或放弃

应使用：

- `timeline`
- `process_flow`

### 10.3 操作流程 / 机制流程

适用内容：

- 套利操作步骤
- 对冲操作步骤
- 保证金追加流程
- 清算流程
- 交易所风控流程

应使用：

- `process_flow`

### 10.4 条件判断

适用内容：

- 市场远期价格高于理论价格还是低于理论价格
- 未来要买入资产还是卖出资产
- 期权是否处于实值状态
- 预期上涨、下跌、大幅波动还是低波动

应使用：

- `decision_tree`

`decision_tree` 只能用于条件分支，不能用于普通分类。

### 10.5 现金流方向 / 风险流向

适用内容：

- A 向 B 支付固定利率
- B 向 A 支付浮动利率
- 双方交换本金和利息
- 清算所成为共同对手方
- 风险暴露从双边关系转成集中清算关系

应使用：

- `cashflow_diagram`

`cashflow_diagram` 只能表示现金流、支付方向、风险转移或关系结构，不能用于普通概念并列。

### 10.6 收益函数 / 期权策略盈亏

适用内容：

- 买入看涨期权收益
- 卖出看跌期权收益
- 牛市价差收益
- 熊市价差收益
- 跨式、宽跨式、蝶式、盒式组合
- 保护性看跌、备兑看涨

应使用：

- `payoff_chart`

payoff chart 应尽量包含 curves、breakEvenPoints、regions、metrics、legs 和 keyTakeaways。没有真实市场数据时，可以使用标准化示意点，但不要伪装成真实数据。

### 10.7 趋势 / 曲线

适用内容：

- 市场规模趋势
- 账户余额变化
- 基差收敛
- 收益率曲线
- 久期与凸性
- 远期价格与现货价格关系

应使用：

- `line_chart`
- `curve_chart`

如果缺少可靠数值，不要伪造真实时间序列。可以使用明确的概念示意，或改用 `chart_explanation`。

### 10.8 无法可靠画出但需要解释的图

适用内容：

- 原图结构复杂
- 轴、曲线或数据无法确认
- 转成图反而会误导
- 只是辅助理解的制度图或长文本图

应使用：

- `chart_explanation`

`chart_explanation` 只能作为保守替代，不能成为逃避可视化重建的默认方式。

## 11. visualBlocks 嵌入位置标准

visualBlocks 不应全部堆在章节底部。它们应尽量出现在对应知识点附近，帮助学生在阅读概念时立即看到公式、流程、案例或图表。

推荐嵌入方式：

- 远期定价后接 `formula_card` 和 `example_box`。
- 套利判断后接 `decision_tree`。
- 期货交易生命周期后接 `timeline`。
- 保证金机制后接 `process_flow` 或 `data_table`。
- 利率互换后接 `cashflow_diagram`。
- 货币互换后接 `timeline` 和 `cashflow_diagram`。
- 期权基础头寸后接 `payoff_chart`。
- 期权策略后接策略对比表和对应 `payoff_chart`。
- 概念并列处接 `comparison_table` 或 `concept_map`。

可以设置“图表汇总”或“可视化复习”区域，但不能只有汇总区。核心 visualBlocks 应跟随核心知识点出现。

## 12. 禁止表达

学生可见内容中禁止出现以下表达：

- 课件展示
- 课件说明
- 课件给出
- 资料中显示
- 资料中给出
- 教材中
- 来源
- source
- chunk
- 页码
- 根据第几页整理
- 来自某文件
- 如图所示但没有对应图
- 见图但没有对应图
- 见表但没有对应表
- 如下表但没有对应表
- 表2.1
- 图2.1
- 用来说明
- 用来判断
- 需要强调
- 这个案例说明了
- 该图展示
- 该表说明
- 图中
- 表中

允许内部 JSON 保留用于校验或导入的非展示字段，但不要把来源、页码、chunk 信息写入页面可见标题、描述、节点文本、block 文案或复习建议中。

## 13. 不确定内容处理

准确性优先于可视化效果。

无法确认数字时，不编造数字。

无法确认案例细节时，不补造完整故事。

无法确认表格全部数据时，不填入猜测值。

无法确认图形坐标时，不伪造真实曲线数据。

无法重建图片时，不伪造 `image` 路径。

如果资料中确实存在重要内容但无法可靠重建，应在 `quality-review.md` 中标明：

- 无法准确重建的图表
- 建议人工截图或人工补充的内容
- 需要人工核对的数据
- 需要人工核对的案例细节
- 可能由 PDF 解析导致丢失的公式、表格或图片

不要为了页面好看牺牲资料真实性。

## 14. quality-review.md 标准

`quality-review.md` 必须写给审核者和后续内容生成者看。它应说明本轮生成的范围、质量、风险和下一步建议。

必须包含：

1. 处理了哪些资料。
2. 每章对应哪些资料。
3. 每章生成了哪些 visualBlocks。
4. 哪些图表被重建为 visualBlocks。
5. 哪些图表无法重建。
6. 哪些数据需要人工核对。
7. 哪些案例细节需要人工核对。
8. 是否存在空引用。
9. 是否存在来源痕迹。
10. 是否通过 schema 校验。
11. 是否建议进入预览。
12. 是否建议导入数据库。

质量报告中还应记录可视化语义检查结果：

- 并列概念不得使用箭头流程展示。
- 箭头仅用于顺序、判断、现金流或操作推进。
- 分类关系优先使用 `comparison_table` 或 `concept_map`。
- 策略收益优先使用 `payoff_chart`。
- 现金流关系优先使用 `cashflow_diagram`。

## 15. 自检要求

生成完成后，内容生成模型必须在交付前自检。自检不是为了写长报告，而是为了避免把明显错误交给用户预览。

必须确认：

1. JSON 符合 `src/lib/ai/framework-schema.ts`。
2. 目标章节已经覆盖。
3. `framework-concise.json` 和 `framework-detailed.json` 都存在。
4. concise 和 detailed 有明显区别。
5. 没有题库内容。
6. 没有学生可见的来源、页码、chunk。
7. 没有空引用。
8. 没有非规范公式，例如 `F0`、`S0`、`ST`、`e^(`、`max(`。
9. 没有把并列概念画成流程。
10. 没有误用 `decision_tree` 表达普通分类。
11. 没有误用 `cashflow_diagram` 表达普通概念关系。
12. visualBlocks 没有全部堆在章节底部。
13. 无法确认的数字、案例和图表已经写入 `quality-review.md`。
14. 不存在伪造图片路径。
15. 不存在为了可视化而编造的公司、数字、案例或关系。

校验时优先使用项目现有 schema 和脚本。如果现有 `validate:content` 不支持 sample/full 子目录，不要覆盖正式目录强行校验，应使用只读方式调用 schema 校验目标 JSON，并在结果中说明。

## 16. 最终输出报告要求

每次生成或增强完成后，回复用户时必须说明：

1. 修改了哪些文件。
2. 处理了哪些资料。
3. concise 包含哪些章节。
4. detailed 包含哪些章节。
5. 每章新增或保留哪些 visualBlocks。
6. 哪些图表仍无法重建。
7. 哪些内容需要人工核对。
8. 是否通过 schema 校验。
9. 是否建议预览。
10. 如何预览。

如果本轮只写文档或只做诊断，也必须明确说明没有修改 JSON、没有修改代码、没有导入数据库。

## 17. 执行优先级

当用户没有特别说明时，后续课程内容生产应按以下优先级执行：

1. 遵守用户当前任务范围。
2. 遵守本文件。
3. 遵守项目现有 schema、docs 和脚本。
4. 遵守已经确认的 sample 标准。
5. 保持生成内容可预览、可校验、可导入。

当本文件与用户当前明确指令冲突时，以用户当前明确指令为准，但必须在回复中说明偏离原因。

当原资料不完整、PDF 解析不可靠或图表无法重建时，不要自行扩大范围、调用在线 API 或编造内容，应保守生成，并把风险写入 `quality-review.md`。
